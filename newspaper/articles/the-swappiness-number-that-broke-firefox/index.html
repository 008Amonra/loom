The Swappiness Number That Broke Firefox

A single kernel parameter, set to the wrong value, turned a working browser into a crash machine.

Firefox crashed. Not once - repeatedly. Tabs closed themselves. The browser restarted with a session restore prompt. The session restore showed dozens of tabs that had been working minutes ago.

The first assumption was too many tabs. A browser with many tabs consumes memory. When memory runs out, the operating system kills processes. Firefox, being the largest process, gets killed first.

But the machine had 16 gigabytes of RAM. Firefox was using 7. The system should have had plenty of room. The crash was not caused by insufficient memory. It was caused by a kernel parameter that was aggressively moving memory to disk.

The Number

The parameter is vm.swappiness. It controls how aggressively the Linux kernel moves memory pages from RAM to swap space on disk.

The default value is 60. This means the kernel balances between keeping pages in RAM and moving them to swap. A lower value (10-30) means the kernel prefers RAM. A higher value (100-200) means the kernel prefers swap.

The value on this machine was 180.

This is not a default. Someone or something set it to 180. At this value, the kernel aggressively moves pages to swap even when RAM is available. The result is constant disk I/O as pages are swapped out and swapped back in - a phenomenon called “thrashing.”

What Thrashing Looks Like

Thrashing is the condition where the system spends more time moving pages between RAM and swap than doing useful work.

The symptoms are specific:

  1. Disk I/O spikes: iostat shows constant write activity to the swap partition
  2. RAM appears full: free -h shows most RAM in use, but much of it is actually cached pages that could be freed
  3. Swap usage grows: The swap partition fills up as pages are moved off RAM
  4. Applications slow down: Every page fault now requires a disk read instead of a memory access
  5. Applications crash: When the swap partition is full, the OOM killer activates and terminates the largest process

On this machine, the swap usage was 7.4 gigabytes out of 19. The RAM was 8.1 gigabytes used out of 16. The system was constantly moving pages between RAM and disk, and Firefox - with its many tabs and large memory footprint - was the primary victim.

The Fix

The fix was a single command:

sudo sysctl vm.swappiness=60

The effect was immediate. Within seconds, the system stopped aggressively swapping. Firefox stopped crashing. The disk I/O dropped. The machine felt responsive again.

To make the fix permanent, the value was added to /etc/sysctl.conf:

vm.swappiness=60

This ensures the value persists across reboots.

Why 180 Exists

The swappiness range is 0-200. Values above 100 are unusual but valid. They tell the kernel to prefer swap even more aggressively than the default.

Some systems ship with high swappiness values for specific reasons:

  • Laptops: aggressive swapping saves battery by keeping more of RAM in a low-power state
  • Servers with swap partitions on fast NVMe: swapping to fast storage is less costly
  • Container environments: aggressive swapping allows more containers to run in limited RAM

On a desktop machine with a spinning disk or a slow SSD, high swappiness is destructive. Every swap operation takes milliseconds instead of nanoseconds. The cumulative effect is a system that feels slow and unstable.

The Diagnostic Path

The diagnostic path from “Firefox crashes” to “swappiness is 180” is not obvious. The symptoms look like insufficient memory. The fix looks like “close some tabs.” The real cause is a kernel parameter that most users never check.

The diagnostic tools are simple:

# Check swap usage
free -h

# Check swappiness
cat /proc/sys/vm/swappiness

# Check which processes are using swap
for pid in /proc/[0-9]*; do
    swap=$(awk '/VmSwap/{print $2}' "$pid/status" 2>/dev/null)
    [ "$swap" -gt 0 ] 2>/dev/null && echo "$swap $pid/$(cat "$pid/comm" 2>/dev/null)"
done | sort -rn | head -10

The first command shows total swap usage. The second shows the swappiness value. The third shows which processes are using the most swap. If Firefox is at the top of the swap list, the problem is likely swappiness, not Firefox.

The Broader Lesson

The swappiness problem is an instance of a general class: a system parameter that was set for a different context and never revisited.

The value 180 might have been correct for a different machine, a different workload, or a different time. When the context changed - different hardware, different applications, different usage patterns - the value became harmful. But no monitor watched it. No alert triggered. The system continued operating with a parameter that no longer made sense.

The lesson is not about swappiness specifically. It is about system defaults. Every system has parameters that were set once and never revisited. Some of them are wrong for the current context. The only way to find them is to look.

Verdict

  • Diagnosis: simple (one command: cat /proc/sys/vm/swappiness)
  • Fix: one command (sudo sysctl vm.swappiness=60)
  • Prevention: check system defaults after installation, especially for desktop machines
  • Impact: high - a single wrong parameter degraded the entire system

The swappiness number that broke Firefox was not a bug. It was a configuration value that was inappropriate for the hardware and workload. The kernel was doing exactly what it was told. The problem was that no one told it to stop.
