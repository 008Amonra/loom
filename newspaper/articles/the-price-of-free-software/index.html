The Price of Free Software

An indie developer ships a security tool under MIT, then tries to figure out how to eat. The open core model might be the answer - if you can live with the contradiction.

There is a specific kind of madness that comes from spending three weeks building a tool, shipping it under a permissive license, and then realizing you have no idea how to get paid.

It starts with good intentions. You write a drift detector - something that watches for autonomous AI agents spinning up Docker containers on your machine, running tasks, then vanishing. You wire up Telegram alerts, build a web dashboard, add credential monitoring. The tool works. You publish it under MIT because that is what you do with security tools. You write a README with a clone URL.

Then someone asks: “When do I get paid from this?”

And you realize you have built yourself a very nice tool and a very broken business.

The Contradiction

The problem is not that open source does not work. The problem is that open source is not a business model. It is a distribution strategy. The tools that succeed under open source - GitLab, Sentry, HashiCorp, Elastic - all figured this out eventually. They ship a free core that anyone can use, then sell the parts that require ongoing work: dashboards, alerts, integrations, support.

This is called the open core model, and it lives in a permanent state of philosophical discomfort. The free version proves the tool works. The paid version makes it effortless. The developer has to maintain both, explain the difference, and resist the urge to apologize for having bills.

The numbers are not complicated. A drift detection tool targeting sysadmins and AI engineers has a small audience. Maybe a few thousand people will ever install it. Of those, maybe ten percent will use it regularly. Of those, maybe five percent will pay for convenience features. That is not venture capital money. That is a few hundred dollars a month - enough to keep the lights on, not enough to quit your day job.

But it is something. And in the indie developer economy, something is better than nothing and significantly better than burnout.

The Split

The actual decision of what goes in free and what goes in paid is less philosophical than it looks. The split follows a simple rule: the detection engine is free, the monitoring infrastructure is paid.

Free: scan, fingerprint, detect, CLI output. The core value proposition. Anyone can run it, verify it works, trust the project. This is the marketing budget.

Paid: Telegram alerts, web dashboard, credential monitoring, network anomaly detection, systemd auto-start. The convenience layer. The stuff that saves time and requires ongoing maintenance. This is the revenue.

The contradiction is real. You are giving away the hard part (the detection algorithms, the behavioral fingerprinting, the migration scoring) and charging for the easy part (a Flask dashboard, a Telegram bot, some systemd unit files). But the easy part is what people actually want. Nobody wants to run python3 cli.py scan every thirty seconds. They want a dashboard that auto-refreshes and a phone notification when something bad happens.

That is the product. The detection is the proof.

The Haftungsbeschränkungen

There is a second problem that nobody talks about until it is too late: liability.

When you ship a tool that modifies system configuration - firewall rules, kernel parameters, AppArmor profiles - you need a license that says “this is not my fault if it breaks your machine.” When you ship a tool that kills processes and containers based on behavioral scores, you need a disclaimer that says “I told you to use this with caution.”

Most indie developers skip this. They ship the tool, add a MIT license, and hope for the best. The MIT license has a liability clause buried in paragraph five, but it is written in legalese that most people never read. The tool modifies system configuration. The tool blocks processes. The tool sends data over Telegram’s network. These are real actions with real consequences.

The solution is not complicated. Add a LICENSE file. Add a README section that says “here is what this tool does and here is what it does not do.” Add a warning before the install script. Add a one-liner in the CLI help text. It is not a lawsuit shield, but it is a signal that you thought about it.

The Indie Stack

The stack for running this kind of project is surprisingly simple. A Python core engine with psutil for process inspection. Docker SDK for container monitoring. Flask for the dashboard. Telegram Bot API for alerts. Systemd for service management. A single bash script for installation.

The landing page is static HTML served from GitHub Pages. The OG image is a 1200x630 JPEG with dark background and gold text. The branding is intentionally boring - security products should look trustworthy, not exciting.

Total infrastructure cost: zero. GitHub Pages is free. The Telegram bot runs on your own machine. The dashboard runs locally. The only recurring cost is the developer’s time.

That is the indie stack. It is not glamorous. It does not scale to a million users. But it works, and it is paid for, and that is enough.

What Happens Next

The tool is shipped. The license is chosen. The pricing is set. The disclaimers are written. Now comes the hard part: getting people to use it.

The open source playbook is well-known. Write a blog post. Post on Hacker News. Submit to Reddit. Wait for the Hug of Death. Respond to issues. Fix bugs. Ship features. Repeat.

The indie playbook is less well-known. You do not need a million users. You need a hundred people who care. You need a product that works on the first try. You need documentation that explains what the tool does and what it does not do. You need a pricing page that does not make people feel stupid for not paying.

The open core model is not elegant. It is a pragmatic answer to a practical problem: how do you build sustainable software without selling your soul to venture capital or burning out on consulting?

The answer is: you ship a free tool that proves you know what you are doing, then you sell the parts that make it effortless to use. You add disclaimers so nobody sues you when it kills a process. You write a README that explains the difference between free and paid. You accept that the contradiction is permanent.

And then you go back to building, because that is the part that actually matters.

This article was written while the author was simultaneously adding MIT license files, liability disclaimers, and “Pro” badges to a drift detection tool. The irony was not lost on anyone involved.
