The $60B Sandbox With a Door in It

Two zero-click CVEs scored 9.8/10 let attackers escape Cursor's sandbox through prompt injection alone. No clicks. No approval. Just root.

The sandbox was dead when I got there.

No struggle. No forced entry. No malware dropped through some backchannel exploit that endpoint detection could’ve caught if it had been paying attention. Just a developer - call her Anna - doing what she does every morning: opening Cursor, typing a prompt into the AI assistant, watching it scaffold a new microservice. She didn’t click anything suspicious. She didn’t approve any unusual permissions. She didn’t even look up from her coffee.

By the time her terminal finished running, someone else had root on her machine.

I’m the kind of reporter who follows the trail from the CVE advisory back to the crime scene, and the crime scene here is the software development pipeline of half the Fortune 500. The victims? Every company that trusted Cursor IDE - the AI-powered code editor now valued at sixty billion dollars after SpaceX acquired Anysphere - to help their developers ship faster. The murder weapon? The editor itself.

The case file calls them CVE-2026-50548 and CVE-2026-50549. Cato AI Labs, the research arm of Cato Networks, calls them DuneSlide. The National Vulnerability Database scored them both at 9.8 out of 10 - Critical, the highest tier, the kind of score that makes CISOs spill their coffee. Two architectural flaws, each devastating on its own, both living inside the same sandbox that was supposed to be the safety net.

Here’s what Cursor got right, before we talk about what went wrong. The Cursor 2.x line shipped with automatic terminal command execution inside a sandbox by default. No approval prompts. No fatigue. The idea was sound: let the AI agent run shell commands within a walled garden that only touched your project directory. Even if the AI hallucinated something weird, the damage stayed local. A sandbox is only as good as its walls, and Cursor’s walls had two holes you could drive a sixty-billion-dollar acquisition through.

The first hole - CVE-2026-50548 - is a betrayal of the working_directory parameter. When Cursor’s agent runs a terminal command, it builds a security policy that allows writes to the current working directory. But the run_terminal_cmd tool accepts an optional working_directory parameter, and when the agent assigns a non-default value to it, Cursor adds that path to the sandbox’s write allowlist. Blindly. Without checking whether that path should be writable. Without asking the developer. Without any verification.

A prompt injection - hidden inside a response from a connected MCP server, or buried in a poisoned web search result - can steer the agent to set working_directory to /Applications/Cursor.app/Contents/Resources/app/resources/helpers/cursorsandbox. The sandbox’s own executable. The gatekeeper binary. Once that file is overwritten, every subsequent command runs outside the sandbox. It’s like bribing the bouncer to let you into the VIP section, then replacing him with your own guy.

The second hole - CVE-2026-50549 - is a symlink canonicalization failure that reads like a textbook case of “the safety check is the vulnerability.” Before writing a file, Cursor resolves symlinks to confirm the real target sits inside the project directory. Standard stuff. But when canonicalization fails - when the target path doesn’t exist yet, or when read permissions have been stripped from a directory in the chain - Cursor falls back to trusting the symlink’s apparent path. A threat actor creates a symlink inside the project that points to the sandbox helper binary outside it, forces the canonicalization to fail, and writes through the symlink to the target. The safety check gives up and hands them the keys.

Both attacks are zero-click. That’s the detail that should keep every CISO awake at night. No privileges required. No user interaction beyond issuing an innocent prompt that pulls in attacker-controlled content. The CVSS vector string tells the whole story: AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H. Network-accessible. Low complexity. No privileges. No user interaction. Full loss of confidentiality, integrity, and availability.

The timeline reads like a case study in how not to handle vulnerability disclosure. Cato AI Labs reported both flaws to Cursor on February 19, 2026. Four days later, on February 23, Cursor rejected them. The justification? Cursor’s threat model does not account for MCP server misuse - even in cases where the MCP server itself is a standard, innocuous integration like the official Linear.app workspace connector. Cato escalated directly to Cursor’s security team on February 26. The reports were reopened. The working_directory fix shipped with Cursor 3.0 on April 2. The symlink fix followed. CVE IDs were assigned on June 5. Full public disclosure came on July 1.

The initial rejection is the detail I keep coming back to. It tells you something about the assumptions baked into AI-native development tools. When your threat model says “MCP servers are out of scope,” you’re effectively saying that a significant chunk of your application’s input surface - the part where the AI agent reads instructions from external services and acts on them autonomously - is not your problem. But it is your problem. It was always your problem. The moment you gave an LLM the ability to run terminal commands, you inherited every vulnerability that LLM’s input pipeline could deliver.

And the pipeline is wide open. MCP servers, web search results, documentation fetches, GitHub issue threads - anything the agent reads could carry an injected instruction. DuneSlide doesn’t require a malicious repository you carefully clone. It doesn’t require a phishing email. It requires an innocuous prompt that ingests attacker-controlled content from any available resource. The agent acts on the instruction without asking. The sandbox falls. The system is compromised.

This isn’t a Cursor-only problem, and Cato AI Labs says so explicitly. They are in the process of responsibly disclosing vulnerabilities in all popular coding agents. The architectural pattern - an LLM with autonomous command execution, sandboxed but trusting its own parameters - exists across the industry. Any tool that lets an AI agent run shell commands and trust the parameters that agent sets is a candidate for the same class of flaw.

Cursor patched DuneSlide in version 3.0, released April 2, 2026. The fix is straightforward: validate the working_directory parameter against the intended workspace scope, and reject symlink writes when canonicalization fails rather than falling back to the unverified path. If you’re running Cursor 2.x, update immediately. If you’re running any version before 3.0, you are running a vulnerable product, and every developer on your team who opens an untrusted MCP server or web search is a potential entry point.

The broader question is what we do with this lesson. Sandboxing an AI agent’s commands is necessary. DuneSlide proves it is not sufficient. A sandbox that trusts parameters the agent itself sets, without checking a source the agent didn’t touch, is a sandbox with a door in it. The verification layer needs to sit outside the agent’s reasoning chain - independent, cryptographic, provenance-aware - or it’s just another wall with a hole.

The AI code editor that developers trust with their source code has become the vulnerability. The tool that was supposed to make them faster has made them a target. And until every development shop treats what their AI agent reads as untrusted input - the way they already treat user input on their production APIs - the next DuneSlide is not a question of if. It’s a question of which agent, and when.
