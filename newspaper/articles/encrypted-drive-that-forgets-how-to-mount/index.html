The Encrypted Drive That Keeps Forgetting How To Mount

LUKS encryption, keyfiles, auto-mount services, and the reality that USB still finds new ways to fail.

An encrypted backup drive should be simple. Plug it in, unlock it, copy files, unplug it.

In practice, the USB stack on Linux has opinions. The device names change between connections. The mapper names shift. The mount point needs a keyfile. The kernel occasionally decides the drive is still in use when it is not. And sometimes the whole USB subsystem locks up, requiring a reboot to recover.

This is a report from inside that failure mode.

The Setup

The drive in question is a USB external disk, LUKS-encrypted, holding backups and cold storage. The encryption is not optional. The drive leaves the house. If it is lost or stolen, the data should be unrecoverable without the keyfile.

The setup looks like this:

  • LUKS encryption on the raw device
  • A keyfile stored at /etc/luks-keys/tb1.key
  • The keyfile is enrolled as a LUKS passphrase
  • A shell script (tb-mount.sh) handles unlock and mount
  • A systemd user service runs the script at login
  • A cron job auto-unmounts after 30 minutes of idle time
  • nofail is set in both /etc/crypttab and /etc/fstab

Every piece of this is reasonable. Every piece has failed at least once.

The Name Problem

Linux names USB drives in the order they are detected. The first drive might be /dev/sdb. The second might be /dev/sdc. But if you plug in a different drive first, the names shift. The backup drive that was sdb becomes sdc.

LUKS encryption makes this worse. The encrypted device gets a mapper name. If the script hardcodes the mapper name, it breaks when the underlying device name changes.

The solution is UUID-based detection. LUKS devices have a UUID. The script can look up the UUID in /dev/disk/by-uuid/ and find the correct device regardless of what sdb or sdc it became.

This works until the mapper name itself changes. The mapper name is derived from the UUID by default, producing a long string like luks-05fa6817-53fa-4481-9718-81132b9b96e7. If the script references a different mapper name, umount and cryptsetup luksClose will fail silently or noisily.

The “Still In Use” Problem

The most common failure is not corruption. It is the kernel believing the drive is busy when it is not.

A process opens a file on the drive. The process exits. The kernel still holds a reference. umount reports “target is busy.” fuser shows nothing. lsof shows nothing. The drive is ghost-locked.

The fix is brute force: fuser -k to kill anything that might be holding the reference, then umount, then dmsetup remove -f to tear down the mapper device, then cryptsetup luksClose to close the encrypted container.

This is not elegant. It is what works.

The USB Stack Lockup

Sometimes the problem is deeper than a stuck process. The USB controller itself stops responding. dmesg shows errors like:

usb 1-4: reset high-speed USB device number 5 using xhci_hcd
usb 1-4: device descriptor read/64, error -71

When this happens, no amount of fuser -k or dmsetup remove will help. The drive is physically unreachable. The only reliable fix is a reboot.

This has happened twice in one week. Both times, the USB port was fine after reboot. The drive mounted cleanly. The data was intact.

The cause is not always clear. It can be a power management issue, a cable problem, a port failure, or a kernel regression. The symptom is always the same: the drive disappears from the system and cannot be brought back without restarting the machine.

The Auto-Mount Layer

To reduce manual intervention, a systemd user service runs tb-mount.sh at login. A loginctl enable-linger command ensures the service runs even without an active TTY session.

The auto-mount works like this:

  1. System boots
  2. User logs in (or linger triggers the service)
  3. tb-mount.sh status checks if the drive is already mounted
  4. If not, it finds the device by UUID, unlocks it with the keyfile, and mounts it
  5. A cron job checks every 10 minutes whether the drive has been idle for 30 minutes
  6. If idle, the cron job runs tb-eject to unmount cleanly

The auto-eject is important. A backup drive that stays mounted indefinitely is a drive that will eventually be caught by a USB lockup. Unmounting it when not in use reduces the window of exposure.

What Actually Happened

On July 14, the drive mounted cleanly after a reboot. The USB stack had been locked up. Reboot fixed it.

On July 15, it happened again. Same symptom. Same fix. The reboot cleared the USB controller state. The drive appeared. The keyfile worked. The mount succeeded.

The pattern suggests a hardware or kernel issue, not a configuration problem. The configuration is correct. The USB controller is intermittently failing to complete a transfer.

The Lesson

Encrypted backup drives on Linux are not plug-and-play. They require:

  • UUID-based device detection
  • Keyfile-based unlock (no passphrase typing)
  • Auto-mount on login via systemd
  • Auto-unmount on idle via cron
  • A kill-everything fallback for stuck processes
  • A reboot as the last resort

None of this is complicated. All of it is necessary. The gap between “encrypted backup” and “reliable encrypted backup” is filled with scripts, services, cron jobs, and the willingness to reboot when the USB stack stops making sense.

Verdict

  • Practicality: high (with scripts)
  • Cost: low
  • Maintenance burden: moderate
  • Reliability: conditional on USB hardware behaving

An encrypted backup drive is a good machine. It is also a machine that needs a surrounding system to stay reliable. The scripts are the system. The reboot is the escape hatch. Together they work. Alone, they do not.
