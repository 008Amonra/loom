The Broken Port and the USB Resurrection

One dead USB port teaches more about hardware debugging than a dozen working ones.

A computer with four USB ports and three working ones is a computer with a mystery. The broken port does not announce itself. It does not fail loudly. It fails quietly, in a way that looks like every other USB problem.

The symptoms are familiar: a device connected to the port does not appear. lsusb shows nothing. dmesg shows an error. The error message is technical, specific, and unhelpful:

usb 1-4: device descriptor read/64, error -71

Error -71 is ETIME. The USB controller sent a request and did not receive a response in time. This can mean the device is broken, the cable is broken, the port is broken, or the USB controller is confused.

The Diagnostic Process

The first step is elimination. Connect the device to a different port. If it works, the device is fine. Connect a different device to the broken port. If it also fails, the port is suspect.

The second step is dmesg. The kernel log records every USB event. A healthy port produces a clean sequence: device connected, device enumerated, device configured. A broken port produces errors at various stages:

  • error -71 at the descriptor stage: the device did not respond to identification
  • error -32 at the transfer stage: the device stopped responding mid-transfer
  • error -110 at the reset stage: the device could not be reset

Each error points to a different failure mode. -71 suggests the device is not communicating. -32 suggests the device is communicating but unreliably. -110 suggests the USB controller cannot reach the device at all.

The Kernel’s Opinion

Linux handles USB through a stack of layers: the hardware controller (xhci_hcd for modern USB), the USB core, and the individual device drivers. When a device fails, the error propagates up through these layers.

The xhci_hcd driver is the most common source of USB errors on modern hardware. It manages the USB 3.0 controller and handles the low-level communication. When it reports an error, the problem is usually at the hardware level: the port, the cable, or the controller itself.

A useful diagnostic command is lsusb -t, which shows the USB device tree. A working device appears as a leaf node with a device number. A failing device does not appear at all, or appears with a device number of 0.

The Port That Works After Reboot

The strangest USB failure is the one that fixes itself.

A port fails. dmesg shows errors. The device does not appear. The machine is rebooted. The same port now works. The device appears. dmesg shows a clean enumeration.

This happens because the USB controller state is reset during reboot. A stuck transfer, a failed reset, or a corrupted descriptor cache can leave the controller in a state where it cannot communicate with new devices. Rebooting clears the controller state and allows fresh communication.

The underlying cause may be a power management issue. Linux aggressively manages USB power, suspending idle ports to save energy. A port that is suspended and then resumed may fail to reinitialize properly. The fix is to disable USB autosuspend:

echo -1 > /sys/bus/usb/devices/usb1/power/autosuspend

Or to add usbcore.autosuspend=-1 to the kernel command line.

The Hardware Conclusion

When a USB port fails consistently across devices, cables, and reboots, the port is physically broken. This is rare on desktop machines but common on laptops and small form-factor computers.

The cause is usually mechanical. USB ports are soldered to the motherboard. Physical stress - inserting a cable at an angle, bumping a connected device, thermal cycling - can break a solder joint or damage the port contacts.

The fix is replacement, which on a small form-factor machine may mean replacing the entire motherboard. The alternative is to use a different port and mark the broken one with a piece of tape.

Verdict

  • Diagnosis cost: zero (dmesg is free)
  • Repair cost: zero to high (reboot to motherboard replacement)
  • Prevention: disable USB autosuspend, handle cables carefully
  • Lesson: dmesg is the most useful tool for USB debugging

A broken USB port is a small failure that teaches a large lesson: hardware problems look like software problems until you check the kernel log. The error codes are specific. The messages are clear. The solution is usually simple. The hard part is knowing to look.
