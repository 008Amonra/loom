The Disk Space That Eats Itself

Root partitions fill up in ways that surprise everyone, including the person who set them up.

A root partition with 28 gigabytes free feels spacious. Then, over the course of a few weeks, it fills up. Not dramatically - no single event consumes the space. It accumulates. Caches grow. Logs accumulate. Swap files expand. Temp directories collect leftovers. One morning, the disk is at 93%, and the question is: where did the space go?

This is a report from inside that disappearance.

The Suspects

Disk space on a Linux machine disappears in predictable ways:

  1. Package manager caches: Every apt install downloads a package. The package is installed. The downloaded copy stays in /var/cache/apt/archives/. Over time, this cache grows to hundreds of megabytes.

  2. Systemd journal: The journal daemon logs everything. On a busy system, the journal can grow to gigabytes. The default configuration has no size limit.

  3. Browser profiles: Web browsers store cache, session data, and downloaded content. A browser with many tabs - or many sessions - can consume gigabytes.

  4. Package manager node_modules: JavaScript projects install dependencies locally. Each project gets its own copy. A node_modules directory can easily reach 300 megabytes.

  5. User-level caches: Tools like LM Studio, Hugging Face, and model managers cache downloaded models. A single 4-bit quantized model can be 4-11 gigabytes.

  6. Swap: When physical RAM is full, the kernel writes pages to disk. A machine with 16GB RAM and aggressive memory usage can generate 10GB of swap.

The Safe Cleanup

Not all disk space can be reclaimed safely. The model cache is a good example: deleting it saves space but requires re-downloading when needed. The journal is another: aggressive truncation loses diagnostic information.

The safe cleanup targets only cached data that can be regenerated:

# Package cache (safe - apt redownloads as needed)
sudo apt clean

# Systemd journal (keep 3 days instead of unlimited)
sudo journalctl --vacuum-time=3d

# Browser caches (browser regenerates)
rm -rf ~/.cache/mozilla/firefox/*/cache2/*
rm -rf ~/.cache/google-chrome/Default/Cache/*

# Node module caches (npm redownloads)
rm -rf ~/.npm/_cacache
rm -rf /tmp/npm-*

# Thumbnail cache (regenerated on demand)
rm -rf ~/.cache/thumbnails/*

Each of these targets data that is explicitly cached - stored for performance, not for correctness. Removing it slows down the next access but does not lose data.

The Unsafe Cleanup

The dangerous cleanup targets data that looks like cache but is not:

  • ~/.cache/lm-studio/ - this is the model cache. Deleting it saves 11 gigabytes and costs hours of re-downloading.
  • ~/.local/share/Trash/ - files in the trash are still on disk. Emptying the trash is safe, but only if you are sure nothing needs to be restored.
  • ~/Downloads/ - downloaded files may be important. Moving them to external storage is safer than deleting them.

The rule is simple: if the data was downloaded and can be re-downloaded, it is safe to delete. If the data was created or cannot be easily replaced, it is not.

The Swap Problem

Swap space is disk space allocated for virtual memory. When RAM is full, the kernel moves inactive pages to swap. This keeps the system running but consumes disk space.

A machine with 16GB RAM and 19GB of swap usage has a problem: the swap file is larger than the physical memory. This happens when processes consume more memory than is available, or when memory is not released after use.

The immediate fix is to reduce swappiness. Swappiness controls how aggressively the kernel moves pages to swap. A value of 60 is default. A value of 180 - which some systems ship with - means the kernel prefers swap over RAM, causing constant disk I/O and premature aging of SSDs.

# Check current swappiness
cat /proc/sys/vm/swappiness

# Set to 60 (default, reasonable)
sudo sysctl vm.swappiness=60

# Make permanent
echo "vm.swappiness=60" | sudo tee -a /etc/sysctl.conf

The Predictable Solution

Disk space management is not exciting. It does not require artificial intelligence or complex algorithms. It requires:

  1. Monitoring: A cron job that checks disk usage every few hours and sends an alert when it exceeds a threshold
  2. Cleanup: A script that removes cached data on a schedule
  3. Limits: Journal size limits, cache size limits, swap configuration
  4. External storage: Large files (models, backups, media) on external drives, not the root partition

The monitoring script can be fifteen lines:

#!/bin/bash
USAGE=$(df / --output=pcent | tail -1 | tr -d '% ')
if [ "$USAGE" -gt 85 ]; then
    echo "Warning: root disk at ${USAGE}%" | \
        mail -s "Disk Alert" user@example.com
fi

This is not sophisticated. It is effective. The disk fills up slowly and fills up quietly. The only defense is watching it.

Verdict

  • Prevention: moderate (requires initial configuration)
  • Recovery: high (safe cleanup frees 500MB-2GB)
  • Monitoring cost: near zero (a cron job and a script)
  • Root cause: caches grow, swap expands, nobody watches

Disk space does not disappear. It is consumed by systems that were designed to use it. The package manager caches packages. The journal logs events. The browser stores sessions. The kernel swaps memory. None of these are bugs. All of them are features that become problems when no one monitors the result.

The disk space that eats itself is not a mystery. It is a system working as designed, in an environment where no one set limits.
